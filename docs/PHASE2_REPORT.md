logging, health checks). Phase 2 added asynchronous PostgreSQL support end to end:

- Async SQLAlchemy engine/session layer (`FastAPI → AsyncSession → PostgreSQL`)
- UUID-based declarative base ready for future business models
- Alembic as the single source of truth for schema changes
- A database health endpoint with safe failure behaviour
- Tests covering configuration, migrations, and the DB health endpoint

No business models, authentication, or AI features were implemented.

## 4. Database architecture

```
FastAPI request
      │
      ▼
get_session (dependency, app/core/database.py)
      │  async with AsyncSessionLocal() as session
      ▼
AsyncSession (async_sessionmaker, expire_on_commit=False, autoflush=False)
      │
      ▼
AsyncEngine (create_async_engine, pool_pre_ping=True)
      │
      ▼
PostgreSQL (asyncpg / postgresql+asyncpg://)
```

Key design points:

- **Single engine** created from settings at import, `pool_pre_ping=True` for
  resilience against dropped connections.
- **`get_session()`** is an async generator dependency yielding an `AsyncSession`
  and guaranteeing it is closed after the request.
- **`dispose_engine()`** is called in the FastAPI lifespan shutdown.
- No generic repository layer — deliberately avoided over-engineering.

## 9. Migration commands

```sh
uv run alembic upgrade head            # apply all migrations
uv run alembic revision --autogenerate -m "describe change"   # create a migration
uv run alembic current                 # show current revision
uv run alembic history                 # show history
uv run alembic downgrade -1            # revert last migration
uv run alembic check                   # detect model/schema drift
```

## 11. Issue found & fixed during testing

The DB health endpoint initially caught only `SQLAlchemyError`. Testing revealed
that asyncpg raises a **raw `OSError`** (connection refused) that is *not*
wrapped as `SQLAlchemyError`, so the handler now catches `Exception` and returns
the same safe 503 response. This was caught by the deterministic 503 test, not
guessed.

## 12. Limitations / assumptions

- Local credentials are the Docker defaults (`postgres:postgres`); they exist
  only in the gitignored `.env`.
- The DB-available health test requires a real PostgreSQL; it skips (does not
  fake a pass) when the database is unreachable.
- One pre-existing framework warning: starlette deprecation notice about
  `httpx` vs `httpx2` in `TestClient`. Harmless, framework-level.
- Docker CLI itself is not usable in this environment (permission denied), so the
  PostgreSQL container was accessed directly through its exposed port; the
  database itself was managed with `asyncpg`.
